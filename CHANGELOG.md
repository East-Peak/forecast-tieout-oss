# Changelog

## Unreleased: the rebuild

The app now runs on a new calculation core, and the old engine is retired (git tag
`pre-rebuild` is the archive).

### Added
- `engine/tieout_core`: one core that reads a company's deals, stage history and roster and writes a tied-out `report.json` and `report.md`: reconciliation to the source files, a fitted forecast with 80% and 95% ranges against two baselines, a back-test, the gap to target, capacity, required pipeline, a hiring and program plan, and two verdicts. Run it with `python -m engine.tieout_core report`.
- A declared report contract (`report.schema.json`, schema version 2.0.0) with cross-field rules, and generated TypeScript types.
- Four named scenarios per company (as signed, demo plan, hires only, program only), each a complete report computed by the core, with a core-computed comparison file.
- `engine/scripts/generate_app_reports.py`, with `--verify` that compares every generated file byte for byte; `generate_data_v2.py` with rebuilt demo data with about two and a half years of history.
- Five screens in place of nine: Forecast, Capacity, Pipeline, Plan and Trust, each answering one question and showing its error or its limits beside its number.
- A binding component, tests that check every bound value against an independent expectation, a stray-digit rule, chart-series checks, mutation tests, and a gate that finds arithmetic in `frontend/src`.
- Redirects from the old addresses: `/bookings` to `/forecast`; `/scenario` and `/targets` to `/plan`; `/inventory` and `/funnel` to `/pipeline`; `/audit`, `/methodology` and `/export` to `/trust`; `/capacity` is replaced in place. The old `?profile=` is read as the company.
- New README screenshots and Open Graph image captured from the new screens (`npm run screenshots`).
- CI runs `npm run verify` and both `--verify` commands.
- Ranges that hold what they claim (Goal 2D, schema version 2.3.0): the simulated 80% and 95% ranges can be stretched away from their median by a lower and an upper factor per tested horizon, each the smallest that would have put at least 90% of the eligible past forecasts inside on that side. A fold is eligible only once its whole horizon had ended; a back-test fold is scored with the factors known at its own date. The thresholds and the adoption rule were committed before any demo company was scored: Mighty Oak Holdings adopts it (pooled 80% coverage 39% simulated, 89% stretched); Sprout Labs and Sapling Industries do not (89% either way). Every range carries a label naming the factor horizon and whether its window was a tested shape (otherwise "extrapolated"); the report gives the decision, the scored dates, what the rule accepted (one-sided, six-month fold counts, floored at zero) and the method. With-plan ranges and every non-range figure are unchanged.
- The Forecast screen shows the label beside each range and how the ranges were checked; the Trust screen shows the decision with its evidence. Browser tests check that the wide tables render as tables at desktop widths.

- The plan editor (Goal 3D). On the Plan screen at desktop widths a fifth choice, "Your plan", opens a form of hires (segment, how many, start month) and programs (name, created pipeline, start month, optional cost and ramp) that starts from the company's demo plan. Apply computes a complete report for it in the browser with the same Python core that wrote the committed reports (Pyodide in a web worker), and every screen shows it, marked "Your plan, computed in your browser; ranges unvalidated". The core's own validation messages appear beside the item it refuses; a start-up or an Apply that takes too long ends in a visible timeout with a retry. Nothing is fetched until the choice is first opened, nothing from another site, and on a phone the choice is absent. The plan lives in memory for the visit only. The editor's files (Pyodide, wheels, the core, one zip per company; about 17 MB on disk, about 10 MB gzipped, once) are built into the site by `npm run build` and are not committed.
- `build_report` is now `prepare` (everything a plan does not touch) then `finish` (the plan section, self-checks, assembly) with a typed state between; every committed report is byte for byte unchanged. Three `np.repeat` counts are cast to the platform integer so the simulation runs on 32-bit WebAssembly.
- The planning worksheet's core (schema version 2.5.0): every report carries a `worksheet` section, computed in `finish` for the as-signed forecast and for each plan, with no simulation. Four operating drivers (win rate of new pipeline, won ARR per new win, creation productivity, cycle length of new pipeline) apply to pipeline created after the as-of date; for each the section gives the current value, the company's own quarter-by-quarter history and its gates (six mature quarters; twenty created deals per conversion or productivity quarter; five wins per size or timing quarter), the change in bookings in both windows at the low and high historical settings (means of the lower and upper halves), "needed alone" (solves, cannot close alone with the reason, or already at or ahead of target; the cycle solve is stepped and states its overshoot) and whether that value lies inside what the company has done. It also restates the two unit actions, the as-signed to working-plan bridge, the summary figures and the as-signed top-down chain, each figure carried with a JSON pointer the contract checks. The definitions and gates were committed before any company was scored. Every other figure in every report is unchanged. No screen uses it yet.
- Worksheet fix round (schema version 2.6.0): a needed-alone setting is written to its driver's places rounded up, and its bookings and overshoot are those of the written value, so entering it reaches the target; "cannot close" is decided by exact bookings and a sub-cent shortfall says so; a cycle with no win-time evidence, or of zero days, has explicit variants with reasons; each driver and each unit action carries a `rank` per window; the section's self-checks count in the software-correct verdict (every report's check count changes); the validator rebuilds every referenced figure with its canonical pointer, derives eligibility and every sentence from fields, recomputes the historical settings, and never raises; `generate_app_reports --verify` replays every committed sensitivity and solve through the whole forward function.

- Actions on a slice, the core (schema version 2.7.0): a plan may carry win-rate actions, each a named change to the win rate of the company or one segment, with a start month, a ramp (0 is at once) and a target probability. An action changes pipeline created from its start, ramping linearly by creation date and holding the target; earlier pipeline and every open deal keep their rates; organic, hire-generated and program creation each get the change once; a company action is the same action in every segment, and a segment's action moves no other segment. Overlapping actions on one driver (the company overlaps every segment), unknown segments, targets outside 0 to 1 and starts not after the as-of month are refused. New report section `driver_actions`: each action's "bookings lost if removed" for the rest of the year and the next twelve months, the joint gain, the reconciliation line with its sentence, the same plan without its driver actions, and for each action the pooled baseline, change in points, resulting rate and where the target sits against the worksheet's low and high ("outside the worksheet's historical settings"); the plan's bridge gains one joint actions step; ranges are re-simulated with the actions in force and say once what they leave out. The swimlane grid shows each lane's resulting win rate and its wins and bookings follow. The browser worker's plan accepts actions. No committed plan has actions, so every committed report differs from before only by the schema version and an empty `driver_actions` section; lanes files are unchanged. No screen uses it yet.

- Actions on a slice, the screen: the plan editor lists win-rate actions beside hires and programs (name, slice, start month, ramp in months, target win rate typed as a percent; the form moves the point in the text and calculates nothing), with the pooled baseline and the worksheet's low and high beside each target, and, for an action as it was applied, the core's change in points, resulting rate and its label ("outside the worksheet's historical settings", never stronger). The core's refusals appear beside the item in its words. After Apply an Actions block shows each action's "bookings lost if removed" for the rest of the year and the next twelve months, the joint gain, the reconciliation line only where it is not zero, and the same plan without its actions; the bridge draws its joint actions step. Two entry points open a draft in the editor that is not applied until Apply: "Add to plan" on the win-rate bar (company, the favorable end of the worksheet's settings; the draft says its value will differ from the bar's, which assumes an immediate company-wide change) and "Plan an action here" in the panel of a win-rate cell of the company or a segment (that slice, target at the pooled baseline, the cell's own number being a dated cohort rate). Under actions the win rate's "needed alone" says the core's limitation sentence, and the win-rate panel adds the core's caveat for actions. Desktop widths only, as the editor is. No committed scenario has an action: the editor is the demo.

- Actions on a slice, polish (schema version 2.8.0): the core's refusals of an action are written for a person (the action's name and the segment's display label; no item numbers, field names or segment keys; a `code` such as `overlap` rides in the structured error beside `section`, `index` and `position`); an action's `affects` sentence writes its month as "October 2026"; the `driver_actions` section carries its definition and a one-sentence `line` even when the plan holds no action, and the form's line under Actions is that sentence; the reconciliation states per window whether it is `material` (it does not round to zero in whole dollars) and the Actions block says the line only then. The worksheet's two one-unit steps are headed "One more hire, one more program" so they are not confused with a plan's actions, and its pills read "Within historical settings" and "Outside historical settings", since the low and high are means of halves of the quarters, not extremes. Every committed report differs only by the schema version and the two added text fields of the empty section.

- Actions on a slice, two more drivers, the core (schema version unchanged at 2.8.0, the change being additive): a plan may also carry an action on the size of a won deal (target in dollars per won deal) and on creation productivity (target in created deals per ramped AE-month where the capacity term is in use, organic deals per day where not). Both are read against the pooled value the worksheet shows and applied to a slice as the same relative change, from the start month, ramping by creation date. A size change leaves how many are won and changes what each books (the simulation scales each sampled won amount by its segment's change on the day its deal was created). A productivity change multiplies the organic creation of the slice (its people and planned hires), not program pipeline, and the extra or missing deals are won at the rate and size the other actions leave and priced at the segment's index over its organic wins, so a company-wide change books exactly what the worksheet's own flex of the pooled value does, programs or not. Actions on different drivers may share a slice and now interact: the reconciliation line is not zero, is marked material, and its sentence (reinforce or overlap) compares sizes, so it reads the same for actions that take bookings away. Each driver's change is measured from the plan with no actions and composed in one place (`driver_actions.effect`), so the order of the plan changes nothing; the same driver on the same slice, or on the company and a segment in it, is still refused. The worksheet's flex of a driver stacks on an action on it (multiplicatively for size and creation, never below zero; only a win-rate action takes the win rate's "needed alone" away). The grid's created deals and created ARR follow a productivity action per segment and owner, its average won ARR a size action. Every committed report, scenario and the `your-plan-actions` editor fixture is byte-identical; `report.schema.json` and the generated types gain the new drivers and the evidence shape for them, and a new editor fixture, `your-plan-three-drivers`, holds a plan with an action on each driver.

### Changed
- American English throughout. The report contract changes with it (schema version 2.0.0): every key, plan file and the scenario id now say `program` (scenario `program-only`); no figure changed (every report compared before and after under the same renaming). Tests keep the old spellings out.
- The line under each company's name is generated from its as-signed report's statuses (year short of, on or ahead of target; whether headcount explains pipeline; whether the fitted forecast beats the simple baselines), in words with no figures; profiles carry no hand-written description.
- The "Is the fitted forecast better than the baselines?" card gives its reason in words and compares the back-test errors at one and three months for the fitted model and each baseline, with which is lower decided in the report (schema version 2.1.0). The report's own sentence stays in `report.json` and `report.md`.
- Demo company data is rebuilt (`engine/data-v2`); the demo companies remain synthetic.
- The two range cards on Forecast keep their figure on one line at desktop widths, and the tables meant to stack only below the large breakpoint lay out as tables from it (their classes were never generated).
- The shared test setup waits up to twenty seconds for asynchronous screens, so a busy machine no longer fails the first test that opens a screen.

### Removed from the app
- The in-browser scenario planner and target-setter solver, the Excel export, the funnel and MQL views and the ARR bridge. Funnel and MQL return with the inbound motion.

## v0.3.0 — 2026-05-XX

### Added
- **TargetSetter page** at `/targets` — inverse-waterfall solver from quarterly bookings target back to required MQL count, with adjustable scenarios + segment splits + per-stage rate provenance display.
- Engine: optional `engine/config/profiles/<id>/scenarios.yaml` with description block for alternative scenarios.
- Profile: optional `assumptions.yaml::target_setter_defaults` (engine-only — feeds runtime-baked observed scenario).
- Snapshot: optional `target_setter.observed_scenario` (engine-baked) and `target_setter.scenarios` (passthrough).
- Schema: validates new optional fields with strict inner shapes (rate bounds 0..1, ACV>0, additionalProperties:false on Scenario items).
- Engine helpers: `monthsForQuarter`, `lastMonthOfQuarter`, `daysUntilQuarterEnd`, `allQuartersFromSnapshot` (snapshot-driven, no fiscal-calendar literals in lib code).
- Validator: catches malformed scenarios.yaml + target_setter_defaults (missing fields, key parity, numeric bounds, root-key typos).

### Demo data
- Acme demo profile ships with `marketing-led` alternative scenario + `target_setter_defaults` for observed scenario.
- Other demo profiles (Sprout, Sapling, Mighty Oak) gracefully render the page with empty state when no TargetSetter config is present.
